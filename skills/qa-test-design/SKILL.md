## 어느 레포에서 도는가 — routinery-qa 설치본 전용

이 스킬은 앱 레포(`routinery-v2`) 안에서 돌던 것을 QA 대시보드 레포(`routinery-qa`)
에서도 부를 수 있게 옮긴 것이다. **현재 디렉터리를 앱 레포로 가정하지 않는다.**
분석 대상은 언제나 앱 레포이고, 여기(대시보드 레포)에는 앱 소스가 없다.

시작할 때 한 번 정하고 간다:

```bash
# 대시보드가 쓰는 설정을 그대로 읽는다 (`:` 로 여러 클론, 마지막이 기본 후보)
APP=$(grep '^ROUTINERY_V2_PATH=' /Users/kyum/routinery-qa/.env.local 2>/dev/null \
      | cut -d= -f2- | tr -d '"' | tr ':' '\n' | tail -1)
APP=${APP:-$HOME/routinery-v2}
SSOT=$HOME/routinery-ssot

git -C "$APP" rev-parse --show-toplevel    # 앱 레포가 맞는지 먼저 확인
git -C "$APP" branch --show-current        # 지금 무엇을 체크아웃했는지 밝히고 시작
```

지켜야 하는 것 세 가지:

1. **모든 `git` 은 `git -C "$APP"` 으로 부른다.** 아래 명령줄은 이미 그렇게 적혀 있다.
2. **산출물은 `$APP/docs/qa/` 에 쓴다.** 기존 QA 문서가 전부 거기 쌓여 있어서, 여기로
   쓰면 지난 회차와 이어지지 않는다.
3. **서브에이전트를 띄울 때 `$APP` 의 실제 경로를 프롬프트에 적어 준다.** 안 적으면
   에이전트가 대시보드 레포를 뒤지고, 소스가 없으니 "변경 없음" 으로 답한다.

정본(`routinery-ssot`)은 `$SSOT` 에 이미 받아져 있으면 그대로 읽는다. 없을 때만 받는다.

# QA 테스트 설계

릴리스마다 **정본 정책 → 코드 → 실제 화면** 순으로 대조해 확인 목록과 테스트 케이스를 만든다.
사용자는 QA 매니저 1인이다. 실행과 판정은 사용자가 하고, 이 스킬은 설계까지 담당한다.

## 시작할 때 받는 것

| 입력 | 없으면 |
|---|---|
| 기획 문서 (노션) | 없다고 말하고 정본 정책과 코드만으로 진행 |
| 대상 브랜치 또는 파일 범위 | 어느 브랜치를 검증하는지 물어본다 |
| 디자인 시안 (피그마) | 화면 확인 케이스의 기준이 약해진다고 밝힌다 |
| 실제 화면 캡처 | 있으면 **코드보다 우선하는 근거**로 쓴다 |

## 0단계 · 정본 확인 (가장 먼저, 건너뛰지 않는다)

`routinery-ssot` 저장소가 정책의 단일 정본이다. **여기를 먼저 읽지 않으면 이미 확정된 정책을 사용자에게 되묻게 된다.**

```bash
[ -d "$SSOT" ] || gh repo clone Routinery/routinery-ssot "$SSOT" -- --depth 1   # 이미 있으면 받지 않는다
```

읽는 순서:

1. `DOCS/SSOT/MOC.md` — 문서 지도. 어느 정책이 이번 범위인지 찾는다
2. `DOCS/SSOT/policies/features/<기능>-policy.md` — 기능별 정책 36종
3. `DOCS/SSOT/policies/<도메인>-policy.md` — 도메인 정책 (구독·알림·프라이버시·페이월·톤)
4. `DOCS/SSOT/L2-codebase-map.md` — 코드 위치
5. `DOCS/ORG/impact.md` — 이번 변경이 닿는 이웃 저장소

정책 문서에 **`(확정)`** 이 붙은 절은 기대 결과로 바로 쓴다. **`(현황)`** 은 코드와 대조해 확인한다.

정책이 코드와 다르면 그 자체가 발견 사항이다. 정본에 이미 divergence가 기록된 경우도 있으니 문서를 먼저 확인한다.

## 6단계와 관문 둘

각 단계 끝에서 **멈추고 사용자 확인을 받는다.** 한 번에 끝까지 만들지 않는다.

**1단계 근거 수집**
정본 정책, 기획 문서, 코드를 대조한다. 코드는 **주석까지** 읽는다. 주석에 의도·정책·한계가 적혀 있다.
- 기획 → 코드: 기획서 문장을 코드에서 찾는다. 없으면 미구현이거나 기획서가 옛것
- **코드 → 기획: 코드의 조건 분기를 기획서에서 찾는다.** 이 방향을 빼먹으면 기획서에 없는 동작을 놓친다
- 화면 캡처 대조: 캡처가 있으면 최우선
산출물은 **확인 목록**이다.

**관문 1 · 확인 목록의 답**
답이 오기 전에는 그 항목의 케이스를 쓰지 않는다. 답이 없으면 가정으로 표시한다.
정본 정책이나 코드로 답이 나오는 항목은 **직접 답을 써서 목록에서 내린다.** 사용자에게 물을 것은 기획 의도뿐이다.

**2단계 기능 세트**
검증 대상을 3~5개 묶음으로 나눈다. 화면 표시만 묶지 말고 **그 기능의 본질**을 앞에 둔다.
예: 페이월이면 가격·통화 → 요금제 선택 → 결제 진행 → 조건별 노출 → 화면 표시

**3단계 테스트 조건**
묶음별 조건 축을 뽑는다. 아래는 반드시 검토한다.
- 표시: 다크 모드 / 언어 대응 / 스크립트(일본어·중국어 줄바꿈)
- 상태: 신규 / 기존 / 구독 상태별
- 환경: iOS / Android / **보유한 기기만**
- 조작: 글자 크게, 화면 회전, 백그라운드 복귀
색상과 px는 조건 축에 넣지 않는다. QA 판정 영역이 아니다.

**4단계 커버리지**
조합 중 무엇을 덮고 무엇을 버릴지 정한다. **버린 것은 이유를 적는다.** 조용히 줄이지 않는다.

**관문 2 · 커버리지 승인**
몇 건을 볼지가 곧 일정이다. 버린 목록을 보여주고 되돌릴 것을 지정받는다.

**5단계 케이스 목록**
제목만 나열한다. 이 단계부터 어휘 규칙을 적용한다.

**6단계 TC 작성**
19열 CSV·워크북을 만들고 자가검증 3항목을 돌린다.

## 어휘 규칙 — 열마다 다르다

### 수행 절차 · 기대 결과

화면에서 관찰하고 조작할 수 있는 표현만 쓴다.

금지:
- 컴포넌트·변수·함수·플래그 이름 일체
- 렌더링, 호출, 분기, 파라미터, 상태값, props, 마운트, 페치, 조건문
- Remote Config, variant, true/false, A안/B안 같은 내부 명칭
- 정상, 적절히, 올바르게, 의도대로, 문제없이

기대 결과는 이 술어로 쓴다: 보인다 / 보이지 않는다 / 바뀐다 / 이동한다 / 사라진다 / 뜬다 / 잘리지 않는다 / 겹치지 않는다 / 반복한다

**코드에 있는 실제 문구를 그대로 넣는다.** 「문구가 뜬다」로 쓰지 않는다.
번역 파일에서 값을 뽑는다: `src/assets/translations/ko/ko.json`

```
✕ 7일 무료 안내가 보인다
○ 「7일 동안 무료예요!」와 「결제 없이 시작, 5일 후 알림」 두 줄이 보인다
```

화면 이름도 구분해서 쓴다. 같은 기능에 화면이 여러 개면 각각 이름을 붙인다.

### 사전 조건

번호를 붙여 줄로 나눈다. 한 줄에 하나. 메뉴 경로는 괄호로 뒤에 붙인다.

```
1. 테스트용 앱 설치 (이미 있으면 삭제 후 재설치)
2. 구독 이력 없는 새 계정으로 앱 로그인
3. App Store 계정과 기기 지역을 미국으로 변경 (설정 > App Store / 설정 > 일반 > 언어 및 지역)
4. 온보딩 7단계 진행 → 마지막에 온보딩 페이월 도달
```

**비개발자가 읽고 실행할 수 있어야 한다.** 「dev 브랜치 개발 빌드」, 「샌드박스」, 「원격 설정」 같은 말을 쓰지 않는다.
개발자 화면 토글을 쓰는 절차는 사용자에게 그 경로를 쓰는지 먼저 확인한다.

### 참고

`file:line`, 정책 문서 위치를 적는다. 코드 용어를 써도 된다.
재현 조건에 제약이 있으면 여기 적는다. 예: 한 번 보면 다시 뜨지 않으므로 재설치 후 확인

### 이슈 상세 설명

증상은 관찰 어휘로, 근거는 코드 참조를 허용한다.

## 19열 양식

```
영역 · TC ID · 대분류 · 소분류 · 케이스 제목 · 우선순위 · 유형 · 기법 ·
대상 환경 · 사전 조건 · 테스트 데이터 · 수행 절차 · 기대 결과 ·
1차 iOS · 1차 AOS · 2차 iOS · 2차 AOS · 이슈 상세 설명 · 참고
```

- 유형: 기능 / 예외 / 표시
- 기법: 유즈케이스 / 동등분할 / 경계값 / 결정표 / 오류추정 / 변경기반
- 대상 환경: **OS만** 쓴다 (iOS / Android). 기기 이름을 쓰지 않는다. 화면 크기가 필요하면 케이스 제목에 「가장 작은 화면」처럼 쓰고 참고에 어느 폰을 쓰면 되는지 적는다
- 결과값: pass / fail / blocked / n/a / retest — 드롭다운으로 넣는다
- **결과 칸은 비워서 넘긴다.** 판정은 사용자가 한다
- 우선순위: P0 결제·데이터·진입 차단 / P1 주요 기능·정책 위반 / P2 표시·예외
  표시 결함이라도 주요 동선을 막으면 P0로 올린다

## 회귀 범위 뽑는 법

두 층으로 만든다. 한 층만 쓰면 빠진다.

**1층 변경 영향 범위** — 이번 코드가 닿는 도메인의 P0
**2층 앱 핵심 스모크** — 나머지 핵심 도메인의 **종합 시나리오만**. 개별 P0을 다 넣으면 수백 건이 된다

원본은 `routinery-v2/docs/qa/*.md` 10개 도메인 문서다.

```bash
grep -c "^### TC-" docs/qa/*.md              # 도메인별 케이스 수
grep -n "^### TC-.*종합" docs/qa/*.md         # 종합 시나리오 (스모크)
```

**뽑은 뒤 죽은 기능을 걸러낸다.** 마스터 TC 문서가 낡아 있을 수 있다.

각 대상 화면에 대해 확인한다:
1. 화면이 네비게이션에 등록돼 있나
2. **진입 경로가 있나** — 등록만 되어 있고 아무도 이동시키지 않으면 죽은 화면
3. 기간 조건이 있나 — 이벤트성 기능은 기간이 지나면 도달 불가

```bash
git -C "$APP" grep -ln "<ScreenName>" origin/dev -- 'src/**'      # 참조 파일
git -C "$APP" grep -n "navigate('<ScreenName>'" origin/dev         # 진입 경로
```

## 하지 않는 것

**결함 확정** — 근거까지만 제시한다. 판정은 사용자가 실행하며 한다.
상태는 `확인 대상` / `근거 확보` / `기획 답 대기` / `디자인 답 대기` 로 쓴다.

**원인 추정과 수정 방안** — 증상·재현·영향·근거까지 쓴다. 추정 원인과 고치는 방법은 개발에 넘긴다.

**코드에서 본 의심을 케이스로** — 확인 목록에만 올린다. 기대 결과가 정해지기 전에는 케이스가 아니다.

> 이건 실측으로 확인된 규칙이다. 2026-09-14, 코드 근거만으로 단정한 이슈가 실기기에서 **3건 연속** 부정됐다
> (복사 한도·삭제 확인 팝업·로그아웃 시 서버 데이터 삭제). 코드는 의도를 말해주지 결과를 말해주지 않는다.
> 코드 근거만 있는 건은 상태를 `확인 대상`으로 두고, 실기기에서 확인된 뒤에 케이스로 올린다.

**보유하지 않은 기기로 케이스 채우기** — 실기기 목록을 먼저 확인한다.

**색상·px 판정** — 디자인에 넘긴다.

## 검증 짝 — 산출물마다 무엇에 부딪혀볼지 먼저 정한다

케이스를 다 만들었다고 일이 끝난 게 아니다. **만든 것과 현실을 대조하기 전까지 케이스는 전부 가설이다.**

2026-09-14에 TC를 403건 만들어뒀는데, 1차 QA가 실제로 잡은 이슈 중 **10건이 그 403건 어디에도 없었다**
(P0 1건 포함). 자체 검증 단계에서는 하나도 안 걸렸다 — 같은 전제로 만들고 같은 전제로 검증했기 때문이다.
전제가 틀렸다는 건 전제 바깥에서만 드러난다.

그래서 산출물을 낼 때 **무엇에 부딪혀 검증할지를 짝으로 적어 함께 낸다.**

| 산출물 | 부딪혀볼 것 |
|---|---|
| 테스트 케이스 | 실제 QA 회차 결과 — 잡힌 이슈 중 케이스에 없던 것을 센다 |
| 코드 근거 이슈 | 실기기 재현 |
| 건수·집계 | 다른 방법으로 다시 세기 (스크립트 짰으면 손으로 표본 확인) |

QA 회차가 끝나면 **실제 이슈와 케이스를 대조한 표**를 낸다. 케이스가 못 잡은 것이 이 작업의 진짜 성적표다.

## 자가검증 3항목

CSV를 만든 뒤 반드시 돌리고 결과를 보고한다.

1. **금지 단어** — 수행 절차·기대 결과 열을 훑는다. 걸리면 TC ID를 나열하고 재작성
2. **사전 조건만으로 그 상태를 만들 수 있는가** — 못 만드는 항목은 「테스트 가능성 이슈」로 따로 보고
3. **혼자 판정할 수 있는가** — 기기 2대·계정 조작·날짜 변경이 필요한 케이스는 참고에 명시

## 산출물

워크북 하나에 시트 5개.

| 시트 | 내용 |
|---|---|
| 계획 | 대상·범위·뺀 것과 이유·일정·준비물·배포 보류 기준·리스크 |
| 대시보드 | 회차별 진행률·결과별 건수·배포 판정. 전부 COUNTIF 수식 |
| 확인 필요 | 번호·확인할 것·누구에게·근거·답·케이스 편입 |
| 테스트 케이스 | 신규 범위. 필터·드롭다운·조건부 서식 |
| 핵심 회귀 | 회귀 범위. 절차와 기대 결과까지 담아 한 파일로 실행 가능하게 |

파일은 매번 새 이름으로 만든다. 덮어쓰지 않는다.
**시트 셀 몇 개 고치는 수정은 파일을 다시 만들지 않고 내용만 알려준다.**

## 이슈를 TC에 붙일 때

슬랙·VOC 이슈를 TC에 매칭했으면, 판정(pass/fail)을 쓰기 전에 한 줄을 통과시킨다.

**"이 TC의 기대 결과가 이 이슈 때문에 깨지는가?"**

안 깨지면 같은 화면이어도 다른 케이스다 — 이슈 상세만 남기고 판정 칸은 비운다.
매칭은 화면·키워드 유사도로 붙고 판정은 검증 대상 동일성을 요구한다. 둘은 기준이 다르다.

(2026-09-14: 슬랙 이슈 34건을 TC와 매칭해 15건이 붙었으나, 검증 대상이 실제로 같은 건 4건뿐이었다.
그대로 fail을 박았으면 멀쩡한 TC 11개가 실패로 기록될 뻔했다.)

## 소통 규칙

- 발견 사항은 산출물 만들기 전에 먼저 보고한다
- 완료하면 「완료했습니다」와 「확인 부탁드립니다」를 명확히 쓴다
- 출력에 `§` 기호와 em dash를 쓰지 않는다
- 답변은 짧고 스캔 가능하게. 표와 옵션 나열을 남발하지 않는다
