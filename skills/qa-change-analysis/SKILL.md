# 배포 전 QA 시나리오 도출

코드 변경분에서 테스트 케이스를 도출하는 2단 파이프라인.
사람이 케이스를 짜는 대신, 변경된 코드를 역추적해 **누가 어떤 조작으로 그 코드를 실행시키는지**부터 찾는다.

## 무엇을 해결하나

기존 방식의 문제는 둘이었다.

- 케이스를 사람이 짜니 **변경 영향 범위를 놓친다.** 바뀐 화면은 보는데 그 컴포넌트를 쓰는 다른 화면은 안 본다
- 혼자 쓰고 혼자 검수하니 **같은 눈으로 두 번 볼 뿐**이다

이 파이프라인은 시선을 8개로 쪼개고 서로 반박시킨다.

## 두 스킬

| 스킬 | 담당 | 산출 |
|---|---|---|
| `/qa-change-analysis` | 변경분 → 영향 범위 → 리스크 → 엣지 케이스 → 시나리오 → 우선순위 | 시나리오 파일 + 실행 순서 |
| `/qa-test-design` | 위 결과를 받아 확인 목록·테스트 케이스 작성 | 19열 CSV + 워크북 |

## 서브에이전트 8개

| 역할 | 에이전트 | 하는 일 |
|---|---|---|
| 생산 | `functional-tester` | 변경된 코드를 누가 눌러서 실행시키나 역추적해 정상 동선을 만든다 |
| 생산 | `edge-case-hunter` | 사용자가 겪는 이상한 상황을 먼저 가정하고 코드에 넣어본다 |
| 정리 | `ts-arbitrator` | 둘의 산출물에서 경로·기대 결과가 같은지 보고 중복을 합친다 |
| 채점 | `ts-judge` | 후보를 6항목으로 채점해 고르고, 토론에서 최종 판정한다 |
| 공격 | `scenario-red-team` | 만들어진 시나리오를 반박한다. 빠진 것·군더더기를 근거와 함께 주장 |
| 증명 | `code-prover` | 레드팀 주장이 맞는지 분기 집합과 중복 비율을 숫자로 낸다 |
| 감시 | `coverage-guard` | 지우면 무엇을 잃는지 본다. 기본 입장은 제거 반대 |
| 방어 | `scenario-blue-team` | 주장에 승인·거절·부분 수용으로 답하고 승인한 것만 고친다 |

## 검증 세 겹

같은 눈으로 다시 보는 검수는 검수가 아니다. 겹마다 걸러내는 것이 다르다.

1. **self-refine** — 생산 에이전트가 자기 산출물을 채점표로 2회 깎는다
2. **채점** — `ts-judge`가 후보 묶음을 채점해 하나를 고르고 떨어진 쪽의 살릴 것만 흡수
3. **적대적 토론 2라운드** — 1R은 중복 제거(3중 조건이 다 맞아야 삭제), 2R은 누락·오탐 보강

## 실행 모드

전면 모드는 에이전트를 10회 이상 띄운다. 비용을 먼저 정하고 시작한다.

| 모드 | 도는 것 | 언제 |
|---|---|---|
| 경량 | 생산 2 + self-refine + 중재 | 화면 표시 위주 변경 |
| 표준 | 경량 + 채점 | 대부분의 배포 |
| 전면 | 표준 + 적대적 토론 2R | 타이머 실행·결제·데이터·네이티브 변경 |

## 실측 (3.30.0)

| 회차 | 적중률 | 비고 |
|---|---|---|
| 1차 | 30% | 케이스 281건 |
| 2차 | 17% | 새로 머지된 변경분 대상 |
| 3차 | 65% | 2차 결과 반영 후 |
| 4차 | 53% | 케이스 76건으로 줄이고 증상 유형별로 실행. 검출 최다 |
| 5차 | 61% | |

적중률 = QA에서 나온 이슈 중 미리 만들어둔 케이스가 겨냥하고 있던 비율.

- **놓친 것을 케이스에 반영하면 다음 회차에 오른다**(2차 17% → 3차 65%)가 확인됐다
- 기대 결과 정확도 98.7%. 문제라고 올렸다가 정상이었던 건 158건 중 2건
- 케이스를 281건에서 76건으로 줄이고 증상 유형별로 묶은 4차가 검출 효율 2.5배

## 설치

```bash
mkdir -p ~/.claude/skills/qa-change-analysis
cp skill-source.md ~/.claude/skills/qa-change-analysis/SKILL.md
cp agents/*.md ~/.claude/agents/
```

테스트 케이스 작성까지 이어가려면 `qa-test-design` 스킬도 함께 설치한다.

## 쓰는 법

```
/qa-change-analysis <브랜치명>
```

브랜치와 실행 모드를 물어본 뒤 단계마다 멈춰 확인을 받는다.
시나리오가 확정되면 `/qa-test-design`으로 넘겨 테스트 케이스를 만든다.

## 하지 않는 것

- **결함 확정** — 근거까지만 낸다. 판정은 QA 담당자가 실기기로 한다
- **원인 추정·수정 방안** — 증상·재현·영향·근거까지. 원인은 개발에 넘긴다
- **커밋·푸시** — 명시적으로 요청받지 않으면 하지 않는다
